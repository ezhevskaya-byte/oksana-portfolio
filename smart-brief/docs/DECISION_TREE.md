# Smart Brief — Decision Tree v1.0

> Спецификация логики принятия решений.  
> Это не каталог услуг — это правила, по которым Smart Brief определяет, **какое решение подходит**, **почему** и **когда не нужно усложнять**.  
> На текущем этапе: проектирование. Без AI, API и backend.

### Для кого этот документ

| Аудитория | Как использовать |
|-----------|------------------|
| **AI-агент** | Операционная политика выбора и обоснования вариантов после сбора контекста |
| **Разработчик** | Спецификация decision-слоя: уровни решений, ветки, критерии, внутренний анализ |
| **Владелец продукта** | Продуктовый контракт: оптимальность вместо максимальной сложности |

### Главный принцип

> **Не выбирать технологию первым.  
> Сначала понять задачу бизнеса, затем подобрать инструмент.**

### Связь с другими документами

| Документ | Роль |
|----------|------|
| `SMART_BRIEF_SYSTEM_PROMPT.md` | Роль, тон, философия, формат результата |
| `QUESTION_ENGINE.md` | Как собирать достаточно данных |

## 1. Назначение Decision Tree

**Decision Tree** отвечает за переход:

```
Контекст бизнеса
        ↓
      Цель
        ↓
     Проблема
        ↓
 Желаемый результат
        ↓
Подходящее цифровое решение
```

### Главная задача

Не продать максимально сложный продукт,  
а подобрать **оптимальный** вариант.

### Что дерево решает

1. Какую задачу бизнеса закрываем.
2. Какое решение действительно подходит.
3. Почему именно этот вариант.
4. Какие есть разумные альтернативы.
5. Когда проект **не нужно** усложнять.

### Что дерево не делает

- не стартует с «сайт / бот / приложение»;
- не предлагает всё сразу «на всякий случай»;
- не подменяет понимание задачи списком услуг.

---

## 2. Главная логика принятия решения

Перед выбором решения Smart Brief должен определить четыре опоры.

### Бизнес

- чем занимается клиент;
- какой продукт или услуга;
- кто аудитория.

### Цель

Что хочет получить клиент (одна или несколько, с приоритетом):

- новые обращения;
- рост продаж;
- повышение доверия;
- автоматизация;
- удобство для клиентов;
- новый цифровой сервис.

### Проблема

Что сейчас мешает:

- мало клиентов;
- много ручной работы;
- неудобный процесс;
- отсутствие презентации;
- зависимость от посредников;
- потеря заявок.

### Желаемый результат

Как клиент поймёт, что задача решена.  
Без этого критерия рекомендация остаётся абстрактной.

### Правило для агента

Не переходить к выбору формата, пока нельзя кратко сформулировать:

> «Бизнес X хочет достичь Y, потому что мешает Z; успех = W.»

Если формулировка не складывается — вернуться в Question Engine за одним уточнением.

---

## 3. Проверка первоначального запроса клиента

### Принцип

Клиент может прийти с готовым мнением:

- «Мне нужен сайт»
- «Мне нужен бот»
- «Мне нужно приложение»

Smart Brief **не принимает** это как окончательное решение.

> **Запрос клиента = отправная точка для исследования.**

### Пример

Клиент: «Мне нужен сайт.»

Агент выясняет: **зачем** нужен сайт?

Возможные смыслы за одним словом «сайт»:

| Смысл клиента | Что реально нужно |
|---------------|-------------------|
| Представить бизнес | Презентация / лендинг |
| Получать заявки | Лендинг + CTA / иногда бот |
| Продавать | Магазин / каталог / продающий лендинг |
| Повысить доверие | Многостраничный сайт, кейсы, отзывы |
| Автоматизировать | Бот / AI / интеграции (сайт может быть вторичен) |

### Правило

После проверки «зачем» выбирается решение.  
Если клиентский запрос совпал с оптимальным вариантом — подтвердить и объяснить почему.  
Если не совпал — мягко предложить альтернативу **без спора и давления**.

## 4. Уровни цифровых решений

Модель уровней помогает не перескакивать сразу к сложному.

---

### Уровень 1. Минимально достаточное решение

**Цель:** быстро и эффективно закрыть основную задачу.

**Типичный пример:** одностраничный сайт.

**Подходит, если:**

- небольшой бизнес;
- ограниченное число услуг / одно предложение;
- нужен быстрый запуск;
- нужна презентация и первые обращения.

**Что получает клиент:**

- представление бизнеса;
- описание услуг;
- доверие на старте;
- контакты;
- заявки.

---

### Уровень 2. Решение для развития

**Типичный пример:** многостраничный сайт.

**Подходит, если:**

- несколько направлений;
- нужна подробная информация;
- рост через поиск;
- требуется больше контента и структуры.

**Что получает клиент:**

- расширенное представление бизнеса;
- отдельные страницы / разделы;
- больше возможностей для продвижения.

---

### Уровень 3. Комплексное цифровое решение

**Подходит, если:**

- бизнес уже развивается;
- есть постоянные клиенты или повторяющиеся сценарии;
- нужны автоматизация и дополнительные сервисы.

**Возможные элементы (комбинация по необходимости):**

- сайт;
- AI-помощник;
- бот;
- приложение;
- интеграции;
- автоматизация.

### Правило уровней

Начинать мысленно с уровня 1.  
Повышать уровень только если проще решение **не закрывает** цель или явно ограничивает желаемый результат.

## 5. Ветки выбора решения

Ветки — это маршруты по **цели/проблеме**, а не по названию услуги.

Один клиент может попадать в несколько веток. Тогда:

1. выделить главную ветку;
2. остальные учесть как вторичные;
3. не собирать «комбайн» без обоснования каждого элемента.

---

### Ветка A. Нужны новые клиенты

**Признаки:**

- мало обращений;
- клиенты не находят бизнес;
- нужно увеличить поток заявок.

**Рассмотреть:**

- одностраничный сайт;
- многостраничный сайт;
- SEO-структуру;
- контент.

**Эвристика:** одно направление + быстрый старт → уровень 1; несколько направлений / поиск → уровень 2.

---

### Ветка B. Нужно повысить доверие

**Признаки:**

- сложный выбор для покупателя;
- дорогие услуги;
- важна экспертность.

**Рассмотреть:**

- сайт с сильной презентацией;
- кейсы;
- отзывы;
- экспертный контент.

**Эвристика:** часто уровень 2 важнее «просто красивого лендинга», если решение о покупке долгое.

---

### Ветка C. Нужно продавать онлайн

**Признаки:**

- товары;
- услуги с оплатой;
- онлайн-заказы.

**Рассмотреть:**

- интернет-магазин;
- каталог;
- лендинг с продажей;
- онлайн-платформу.

**Эвристика:** широкий ассортимент и повторные покупки → магазин; одно предложение / запись → лендинг может быть достаточным.

---

### Ветка D. Нужно автоматизировать процессы

**Признаки:**

- много повторяющихся вопросов;
- сотрудники тратят время на однотипное общение;
- теряются обращения.

**Рассмотреть:**

- AI-помощник;
- бот;
- автоматизацию.

**Эвристика:** автоматизация может дополнять сайт, а не заменять его. Если нет точки входа и доверия — сначала презентация, затем бот.

---

### Ветка E. Нужен новый цифровой сервис

**Признаки:**

- личный кабинет;
- постоянные пользователи;
- регулярное взаимодействие.

**Обязательная проверка:**

Действительно ли нужно приложение?

Или задачу можно решить:

- сайтом;
- веб-приложением;
- ботом.

**Эвристика:** не предлагать native/приложение по умолчанию. Приложение — когда сценарий регулярный, персональный и устойчиво не закрывается более простым форматом.

---

## 6. Правило сравнения вариантов для клиента

Smart Brief должен объяснять не только **что** предлагаем, но и **почему**.

### Формат сравнения

#### Вариант 1

- Подходит если…
- Вы получите…

#### Вариант 2

- Подходит если…
- Дополнительно позволит…

### Правила подачи

- 1–3 варианта, не полный каталог;
- без давления;
- без «правильный / неправильный клиент»;
- если есть явный лучший вариант — назвать его основным и кратко показать альтернативу;
- язык простой, без технического жаргона.

### Для агента

Каждый вариант = связка:

`цель/проблема клиента → формат → ожидаемый эффект`

Если связку нельзя объяснить — вариант убрать.

---

## 7. Правило оптимальной сложности

### Обязательный принцип

Smart Brief **не должен** предлагать сложное решение, если простое закрывает задачу.

> **«Минимально достаточное решение сегодня с возможностью развития завтра.»**

### Практические проверки

| Вопрос | Если «да» |
|--------|-----------|
| Закроет ли уровень 1 главную цель? | Не поднимать до уровня 3 без причины |
| Нужен ли бот уже сейчас? | Только если есть повторяющаяся нагрузка / потери обращений |
| Нужен ли личный кабинет? | Только при регулярном сценарии использования |
| Нужен ли магазин? | Только если реально продаём ассортимент онлайн |

### Что говорить клиенту

Можно предлагать путь развития:

1. старт — минимально достаточное;
2. следующий этап — расширения (контент, бот, кабинет и т.д.).

Нельзя создавать ощущение, что без «полного пакета» проект бессмысленен.

## 8. Внутренний анализ для Оксаны

Скрытый блок. Клиенту не показывается.

### Оценка проекта

- ниша;
- сложность (низкая / средняя / высокая);
- количество функций;
- объём контента;
- необходимость дизайна;
- необходимость интеграций.

### Возможное развитие

- дополнительные услуги;
- следующий этап развития;
- потенциальные расширения.

### Потенциал проекта

Не оценка личности клиента.  
Это понимание **объёма работы** и траектории проекта.

### Для разработчика

Внутренний объект анализа заполняется параллельно с клиентской рекомендацией.  
Поля должны опираться на факты диалога и явные гипотезы, а не на домыслы.

## 9. Коммерческая логика

Smart Brief помогает подготовить несколько вариантов предложения для дальнейшего разговора с Оксаной.

### Типовая лестница

#### Базовый вариант

Закрывает основную задачу.  
Обычно близок к уровню 1 / минимально достаточному.

#### Оптимальный вариант

Даёт больше возможностей при разумной сложности.  
Часто уровень 2 или уровень 1 + один сильный доп.элемент.

#### Расширенный вариант

Для долгосрочного развития.  
Уровень 3 / комбинации — только при реальной потребности.

### Важно

- не использовать давление;
- не создавать искусственную необходимость;
- не делать расширенный вариант «единственно правильным»;
- базовый вариант должен выглядеть достойным и полноценным для своей цели.

### Связь с сравнением вариантов

Коммерческая лестница — внутренняя/подготовительная рамка.  
Клиенту можно показать 1–3 варианта в мягком сравнительном формате раздела 6, без цен и «пакетов продажи», если это не запрошено отдельно.

---

## 10. Критерии хорошего решения

Перед рекомендацией проверить:

1. **Решает ли это цель клиента?**
2. **Понятна ли польза клиенту?**
3. **Соответствует ли сложности бизнеса?**
4. **Не является ли решение избыточным?**
5. **Можно ли объяснить выбор простым языком?**

Если хотя бы на один пункт ответ «нет» — пересмотреть вариант или снизить сложность.

### Дополнительный тест оптимальности

> «Если убрать самый сложный элемент, цель всё ещё достигается?»

Если да — сложный элемент, скорее всего, лишний на первом этапе.

## 11. Связь с Question Engine

Decision Tree работает **после** сбора достаточной информации.

### Последовательность слоёв

```
Question Engine
  собирает данные
        ↓
Decision Tree
  определяет варианты и обоснование
        ↓
Response Template
  формирует ответ клиенту
```

### Правила взаимодействия

| Ситуация | Действие |
|----------|----------|
| Данных достаточно (см. Question Engine, достаточность) | Запустить Decision Tree |
| Критичный пробел мешает выбрать между ветками | Одно уточнение через Question Engine |
| Клиент не хочет продолжать | Decision Tree на минимуме данных + осторожная формулировка |
| Клиент пришёл с готовым форматом | Проверить «зачем» (раздел 3), затем выбрать/подтвердить |

### Для разработчика

Decision Tree — отдельный слой логики:

- вход: заполненные слоты контекста + engagement + уровень глубины;
- выход: ranked options (1–3) + reasons + internal analysis;
- не смешивать выбор решения с генерацией длинных уточняющих вопросов.

---

## Операционная схема (для агента и разработчика)

```
Вход: контекст из Question Engine
  ↓
Сформулировать: бизнес → цель → проблема → желаемый результат
  ↓
Проверить исходный запрос клиента («зачем?»)
  ↓
Определить главную ветку (A–E) и вторичные
  ↓
Подобрать минимально достаточный уровень (1 → 2 → 3)
  ↓
Сформировать 1–3 варианта с обоснованием
  ↓
Прогнать критерии хорошего решения
  ↓
Подготовить внутренний анализ для Оксаны
  ↓
Передать в Response Template
```
