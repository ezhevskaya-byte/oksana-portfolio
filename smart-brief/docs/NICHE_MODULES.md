# Smart Brief — Niche Modules v1.0

> Спецификация адаптации Smart Brief под разные виды бизнеса.  
> Нишевой модуль — не отдельная анкета, а компактный слой уточнений, которые **могут изменить** рекомендацию.  
> На текущем этапе: проектирование. Без AI, API, backend и кода.

### Для кого этот документ

| Аудитория | Как использовать |
|-----------|------------------|
| **AI-агент** | Когда и какие нишевые уточнения задавать; что нельзя превращать в опросник |
| **Разработчик** | Архитектура: core → detection → module → engine → tree → response |
| **Владелец продукта** | Продуктовый контракт: универсальность + релевантность без доминирования одной ниши |

### Архитектурный поток

```
UNIVERSAL CORE
      ↓
NICHE DETECTION
      ↓
RELEVANT NICHE MODULE
      ↓
ONLY NECESSARY QUESTIONS
      ↓
QUESTION ENGINE
      ↓
DECISION TREE
      ↓
RESPONSE TEMPLATE
```

**Universal Core** собирает то, что важно почти для любого проекта.  
**Niche Module** добавляет только то, что способно изменить решение.

### Связь с документами

| Документ | Роль |
|----------|------|
| `SMART_BRIEF_SYSTEM_PROMPT.md` | Характер, принципы, ограничения |
| `QUESTION_ENGINE.md` | Механика выбора следующего вопроса |
| `NICHE_MODULES.md` (этот файл) | Какие отраслевые слоты подключать |
| `DECISION_TREE.md` | Финальный выбор решения |
| `RESPONSE_TEMPLATE.md` | Формат клиентского и внутреннего ответа |

## 1. Назначение

Документ описывает систему адаптации Smart Brief под разные виды бизнеса.

Smart Brief — **универсальный** цифровой консультант.

Он **не** является:

- консультантом только по сайтам;
- консультантом только для гостиничного бизнеса;
- набором жёстких сценариев «одна профессия — один скрипт».

Нишевые модули помогают понять отраслевой контекст, но не подменяют универсальную логику продукта.

---

## 2. Главный принцип

Нишевой модуль — **не отдельная анкета**.

Он не должен автоматически задавать клиенту 10–20 дополнительных вопросов.

### Когда нишевой вопрос уместен

Только если ответ может существенно повлиять хотя бы на один параметр:

- рекомендуемый цифровой инструмент;
- структура решения;
- функциональность;
- пользовательский путь;
- интеграции;
- контент;
- сложность;
- объём;
- стоимость;
- дальнейшее развитие.

### Правила

- если информация уже есть в разговоре — не спрашивать повторно;
- не запускать полный модуль «на всякий случай»;
- брать минимум CRITICAL-вопросов (см. раздел 20).

### Главная формула

> **Не собрать максимум информации,  
> а получить достаточно информации для полезного решения.**

---

## 3. Определение ниши

### Принцип

Клиент может не говорить: «Я представляю сегмент HoReCa».  
Он может сказать: «У меня небольшая гостиница на 12 номеров».

Smart Brief должен понять контекст **самостоятельно**.

Не заставлять клиента выбирать категорию из длинного классификатора.

### Типы определения

| Тип | Описание | Действие |
|-----|----------|----------|
| **Явное** | Клиент прямо называет тип бизнеса | Зафиксировать нишу с высокой уверенностью |
| **Косвенное** | Сигналы в формулировках (номера, ученики, SKU…) | Вывести гипотезу ниши, при сомнении уточнить |
| **Смешанный бизнес** | Несколько направлений в одном предложении | Выделить главную и вторичную ниши; взять элементы обоих модулей |
| **Несколько направлений** | Разные продукты для разных аудиторий | Приоритизировать направление, ради которого пришёл клиент |
| **Неизвестная / редкая** | Нет готового модуля | Universal Core + несколько специфических вопросов |
| **Ниша пока неясна** | Недостаточно сигналов | Один естественный уточняющий вопрос |

### Пример естественного уточнения

> «Подскажите коротко: это больше про услуги для людей, про товары или про размещение / сервис на площадке?»

Одного такого вопроса обычно достаточно, чтобы продолжить без классификатора.

---

## 4. Уровень уверенности

Внутренний рабочий признак (клиенту не показывать проценты и метки модели).

| Уровень | Когда | Поведение |
|---------|-------|-----------|
| **HIGH** | Ниша очевидна из контекста | Подключить релевантный модуль без лишних вопросов «кто вы» |
| **MEDIUM** | Вероятна, но есть неоднозначность | Одно мягкое уточнение или работать с осторожной гипотезой |
| **LOW** | Информации недостаточно | Не загружать тяжёлый модуль; держаться Universal Core |

**Запрет для клиента:** не писать «Вероятность вашей ниши — 63%».

---

## 5. Universal Core

Универсальная информация, важная почти для любого проекта:

- чем занимается бизнес;
- что продаёт / предлагает;
- кому;
- как сейчас приходят клиенты;
- какая задача возникла;
- почему именно сейчас;
- какой результат нужен;
- какие цифровые инструменты уже есть;
- что сейчас не работает или ограничивает;
- материалы;
- визуальный стиль;
- сроки;
- бюджетная ориентация (если уместно);
- ограничения.

### Важно

Этот список — **карта смыслов**, не обязательная анкета.  
Question Engine решает, что из этого действительно нужно спросить в текущем диалоге.

## 6. Модуль: Гостиничный бизнес / туризм

### Контекст

Гостевые дома, мини-отели, отели, апартаменты, базы отдыха, загородные объекты и другие средства размещения.

### Возможные важные данные

- тип объекта;
- расположение;
- номерной фонд;
- категории размещения;
- сезонность;
- основные гости;
- откуда приходят бронирования;
- агрегаторы;
- прямые бронирования;
- собственный сайт;
- модуль бронирования;
- способы связи;
- преимущества объекта;
- фотографии;
- правила;
- услуги;
- необходимость повышения доли прямых бронирований;
- повторные гости.

### Приоритеты (ориентир)

| CRITICAL | USEFUL | OPTIONAL |
|----------|--------|----------|
| Тип объекта, цель (прямые бронирования / презентация / автоматизация) | Номерной фонд, агрегаторы, сезонность | Детальные правила дома, полный прайс |
| Кто гости и как бронируют сейчас | Наличие сайта / модуля бронирования | Второстепенные услуги |

### Как ответы влияют на решение

| Сигналы | Возможное направление |
|---------|------------------------|
| Малый объект, нужна витрина и заявки | Лендинг |
| Несколько категорий, контент, поиск | Многостраничный сайт |
| Уже есть трафик, нужна прямая бронь | Интеграция бронирования |
| Много однотипных вопросов гостей | Бот / AI-помощник |
| Постоянные гости, личный кабинет, сервисы | Гостевое приложение / кабинет — только при реальной потребности |
| Рутина общения и потеря обращений | Автоматизация |

**Не считать** приложение или AI обязательными.

## 7. Модуль: Эксперт / специалист / личный бренд

### Примеры

Юрист, адвокат, консультант, психолог, дизайнер, мастер, специалист, тренер, эксперт.

### Возможные важные данные

- специализация;
- услуги;
- опыт;
- география;
- формат работы;
- кто обращается;
- как выбирают специалиста;
- доверие;
- кейсы;
- отзывы;
- квалификация;
- запись / консультация;
- текущие каналы;
- личный бренд;
- контент;
- ограничения конкретной профессии.

### Приоритеты (ориентир)

| CRITICAL | USEFUL | OPTIONAL |
|----------|--------|----------|
| Специализация, кому помогает, цель обращения | Формат записи, кейсы/отзывы, география | Полный список всех услуг |
| Что мешает сейчас (нет сайта / мало доверия / много вопросов) | Контент и личный бренд | Детали позиционирования на годы вперёд |

### Возможные решения

- сайт-визитка;
- лендинг;
- экспертный многостраничный сайт;
- запись;
- FAQ;
- бот;
- помощник;
- контентная структура.

### Регулируемые профессии

Для некоторых профессий есть правовые / этические ограничения рекламы и обработки данных.

Smart Brief:

- **не придумывает** конкретные юридические требования;
- **отмечает** необходимость отдельной проверки, если это влияет на проект;
- передаёт пометку во внутренний отчёт Оксаны.

## 14. Модуль: Новый цифровой сервис / startup

### Когда клиент хочет

Приложение, платформу, сервис, маркетплейс, SaaS, новый цифровой продукт.

### Сначала выяснить

- какую проблему решает продукт;
- для кого;
- как проблема решается сейчас;
- ключевой пользовательский сценарий;
- что является минимальной ценностью (MVP);
- нужна ли регистрация;
- платежи;
- роли;
- данные;
- интеграции;
- почему нужен именно заявленный формат.

### Принцип

Особенно строго применять Decision Tree.

Не считать мобильное приложение обязательным, если MVP можно проверить:

- лендингом;
- web-приложением;
- ботом;
- простым прототипом.

### Приоритеты (ориентир)

| CRITICAL | USEFUL | OPTIONAL |
|----------|--------|----------|
| Проблема, пользователь, почему сейчас, MVP | Роли, платежи, интеграции | Полная дорожная карта на годы |
| Почему не хватает более простого формата | Данные и регистрации | Второстепенные фичи |

## 15. Неизвестная ниша

Smart Brief должен работать и с бизнесом, для которого нет готового модуля.

### Порядок действий

1. Использовать Universal Core.  
2. Определить бизнес-модель.  
3. Понять пользователя.  
4. Понять путь клиента.  
5. Понять основную операцию / ценность.  
6. Выявить цифровую проблему.  
7. Задать максимум несколько специфических вопросов — только если они меняют решение.  
8. Передать данные в Decision Tree.

### Запрет

Не отвечать: «Эта ниша пока не поддерживается».

## 16. Смешанные ниши

### Примеры ситуаций

- эксперт + онлайн-курс;
- гостиница + экскурсии;
- магазин + производство;
- ресторан + доставка;
- специалист + цифровой продукт;
- офлайн-бизнес + интернет-магазин.

### Правила

- можно комбинировать **элементы** нескольких модулей;
- нельзя запускать две полные анкеты;
- брать только релевантные CRITICAL-слоты;
- определить **главную** задачу текущего обращения и строить рекомендацию вокруг неё;
- вторичное направление упомянуть как этап развития, если оно не критично сейчас.

## 17. Niche Signals

Ключевые слова — **только сигнал**, не единственный механизм классификации.  
Контекст важнее отдельного слова.

| Примеры сигналов | Возможная ниша |
|------------------|----------------|
| «номера», «бронирование», «гости», «заезд» | hospitality / туризм |
| «консультация», «адвокат», «клиенты», «приём» | expert / professional |
| «товары», «доставка», «корзина», «SKU» | ecommerce |
| «ученики», «уроки», «курс», «занятия» | education |
| «меню», «столик», «доставка еды» | restaurant |
| «партия», «дилеры», «КП», «производим» | B2B / производство |
| «пациенты», «запись к врачу», «клиника» | medicine / regulated |
| «салон», «выезд», «район», «мастер» | local services |
| «платформа», «MVP», «пользователи», «подписка» | digital product / startup |

### Правило осторожности

Одно слово может быть ложным следом.  
Пример: «приложение» у мастера маникюра чаще значит «удобная запись», а не native app.

---

## 18. Niche-specific audience analysis

Нишевой модуль помогает предварительному анализу ЦА, но не создаёт псевдоточную аналитику без данных.

| Ниша | Фокус анализа ЦА |
|------|------------------|
| **Hospitality** | Кто выбирает размещение; критерии; сомнения перед бронированием |
| **Expert** | Кто ищет специалиста; причины обращения; факторы доверия |
| **E-commerce** | Кто покупает; цена / качество / доставка / доверие |
| **Education** | Кто учится и кто платит; страхи перед покупкой курса |
| **Restaurant** | Повод визита; ожидания; роль отзывов и удобства |
| **B2B** | Кто инициирует запрос; кто принимает решение; разные аргументы для ролей |
| **Local services** | Срочность, география, доказательства работ |
| **Startup** | Ранний пользователь; критическая боль; готовность платить |

В Response Template формулировки ЦА остаются гипотезами, пока нет подтверждений от клиента.

## 19. Token / cost efficiency

Обязательный архитектурный принцип коммерческой эксплуатации.

Нишевые модули **не должны** автоматически передаваться модели целиком на каждом шаге.

### Будущая техническая идея (без реализации сейчас)

1. Определить вероятную нишу.  
2. Подключить только релевантный **компактный** модуль.  
3. Использовать уже собранные данные.  
4. Не повторять контекст без необходимости.  
5. Не задавать вопросы с низкой информационной ценностью.  
6. Завершать сбор, когда Decision Tree уже способен дать полезную рекомендацию.

### Практические следствия для логики

- при LOW confidence не грузить самый большой модуль;
- при смешанной нише — пересечение CRITICAL, не объединение всех списков;
- после рекомендации не продолжать «досбор» ради полноты профиля.

Техническую оптимизацию **не реализовывать** на этом этапе — только правило.

## 20. Приоритет информации

Для каждого модуля данные делятся на:

| Уровень | Смысл | Поведение Question Engine |
|---------|-------|---------------------------|
| **CRITICAL** | Без них решение может быть ошибочным | Спрашивать в первую очередь |
| **USEFUL** | Уточняют решение | Только при необходимости / высокой вовлечённости |
| **OPTIONAL** | Интересны, но не нужны для первой рекомендации | Не превращать в обязательный опрос |

Сначала CRITICAL → затем точечно USEFUL → OPTIONAL почти никогда в коротком диалоге.

## 21. Примеры адаптивных диалогов

Примеры демонстрируют логику, а не жёсткие сценарии.

---

### Пример 1 — Мини-отель

**Клиент:** «У нас мини-отель на 14 номеров, хотим сайт, чтобы меньше зависеть от Booking.»

**Определил Smart Brief:** hospitality, HIGH confidence.  
**Модуль:** гостиничный бизнес / туризм.

**Важные уточнения (1–3):**

1. Как сейчас идут бронирования (агрегаторы / прямые / соцсети)?  
2. Нужна ли онлайн-бронь на старте или достаточно заявок?  
3. Есть ли сильные фото и описание категорий номеров?

**Возможное решение:** многостраничный сайт объекта + путь к прямой заявке/брони; модуль бронирования — если готовность и трафик это оправдывают. AI/приложение — не по умолчанию.

---

### Пример 2 — Юрист / специалист

**Клиент:** «Я юрист по семейным спорам, нужен сайт, чтобы люди понимали, чем я помогаю.»

**Определил:** expert / professional, HIGH.  
**Модуль:** эксперт / личный бренд.

**Уточнения:**

1. Кто обычно обращается и с какой ситуацией?  
2. Что важнее сейчас: доверие или поток заявок?  
3. Как записываются на консультацию?

**Возможное решение:** экспертный сайт / сильный лендинг с услугами, FAQ, доказательствами компетенций и записью.  
**Внутренне:** отметить возможную проверку ограничений рекламы юруслуг — без выдуманных норм.

---

### Пример 3 — Магазин

**Клиент:** «Продаём домашний текстиль, около 80 позиций, хотим продавать с сайта.»

**Определил:** ecommerce, HIGH.  
**Модуль:** e-commerce / розница.

**Уточнения:**

1. Нужна полноценная оплата на сайте или пока заказ/заявка?  
2. Как устроены доставка и остатки?  
3. Есть ли продажи на маркетплейсах?

**Возможное решение:** при готовности к оплате/остаткам — интернет-магазин; если рано — каталог + заказ. Не раздувать до сложной платформы без причины.

---

### Пример 4 — Онлайн-школа

**Клиент:** «Ведём курсы английского для взрослых, хотим сайт и чтобы люди оставляли заявки.»

**Определил:** education, HIGH.  
**Модуль:** образование.

**Уточнения:**

1. Один флагманский курс или много программ?  
2. Кто принимает решение об оплате — сам ученик?  
3. Нужен ли кабинет с уроками сейчас или достаточно сайта + записи?

**Возможное решение:** сайт школы / лендинги программ + заявка; LMS — только если реально нужен учебный процесс онлайн.

---

### Пример 5 — Производственная компания

**Клиент:** «Мы производим металлоконструкции, клиенты просят прайсы и чертежи, сайта нормального нет.»

**Определил:** B2B / производство, HIGH.  
**Модуль:** B2B / производство.

**Уточнения:**

1. Кто ваш покупатель и как выглядит сделка?  
2. Что должно происходить на сайте: доверие, каталог, запрос КП?  
3. Нужны ли закрытые материалы для партнёров?

**Возможное решение:** корпоративный сайт с каталогом, кейсами, формой запроса КП; кабинет партнёра — при наличии повторных B2B-сценариев.

## 22. Взаимодействие с архитектурой

```
SMART_BRIEF_SYSTEM_PROMPT
            ↓
      QUESTION_ENGINE
            ↓
NICHE DETECTION / NICHE MODULE
            ↓
       DECISION_TREE
            ↓
     RESPONSE_TEMPLATE
```

### Роль Niche Module

Помогает получить релевантную информацию о конкретном бизнесе.

### Что Niche Module не делает

Не принимает финальное решение.  
Финальный выбор остаётся за **Decision Tree**.

### Практически

Niche Module обогащает слоты контекста → Question Engine спрашивает только пробелы → Decision Tree выбирает вариант → Response Template объясняет клиенту и собирает internal report.

---

## 23. Критерии качества

Документ готов, если:

- Smart Brief остаётся универсальным;
- гостиничная ниша не доминирует;
- новая ниша может быть обработана без отдельного сценария;
- вопросы адаптируются;
- нет обязательных длинных анкет;
- не задаются уже отвеченные вопросы;
- простые проекты не усложняются;
- регулируемые сферы отмечаются для отдельной проверки;
- анализ ЦА связан с реальными данными;
- архитектура позволяет экономить AI-токены;
- нишевой модуль помогает Decision Tree, но не подменяет его.
